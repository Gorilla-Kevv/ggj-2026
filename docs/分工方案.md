## 四、协作规范

### Git分支策略

```
main
  └── dev
        ├── feature/core          (程序A: T1-T8, T10)
        ├── feature/gameplay      (程序B: T9, T12-T13, T15-T16, T18-T19, T21)
        ├── feature/levels        (关卡组: T11, T14, T17, T20, T22)
        └── feature/audio         (T23)
```

- 每人从 `dev` 开分支，完成后提 PR
- 每日至少合并一次 `dev`，确保不积压冲突
- 关卡组和程序B的交互物体场景需用同一分支或频繁同步

### 文件所有权

| 目录 | 所有者 | 备注 |
|------|--------|------|
| `src/autoload/` | 程序A | 任何人可读，修改需告知A |
| `src/actors/player.gd` | 程序A | 程序B的敌人需调用 `player.die()` |
| `src/actors/enemies/` | 程序B | 使用A提供的 `BaseEnemy` |
| `src/interactables/` | 程序B | 使用A提供的 `Global.selected_target` |
| `src/environment/` | 程序B | |
| `src/systems/` | 程序A | `wind_system.gd` 是核心，修改需谨慎 |
| `src/ui/` | 程序A (HUD) + 程序B (boss_health) | |
| `src/level/` | 程序A | |
| `src/scenes/level_*.tscn` | 关卡组 | 引用程序A/B提供的脚本 |
| `assets/` | 美术组 | 程序可引用，不可直接修改 |

### 接口约定（写代码前必读）

**关卡组需要知道的：**
- 所有可交互物体在场景中放置后，自动加入 `"interactable"` 组
- 关卡场景根节点必须挂 `level_manager.gd`，设置 `next_level_path`
- 检查点用 `checkpoint.gd` 场景，直接拖入关卡
- 出生点用 `Marker2D` 节点名 `"SpawnPoint"`

**美术组需要知道的：**
- TileMap 贴图集使用 32×32 像素单元
- 主角风滚草需要至少4帧旋转动画 + 1帧闲置
- 敌人精灵需区分：闲置/移动/攻击（Boss需要涡轮开关两态）
- 粒子贴图使用白色基础贴图，颜色在引擎内调

## 五、风险与缓冲

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| 风力手感调不出来 | 中 | 核心玩法崩塌 | D3前若手感不达预期，简化操作：移除R键切换，风仅吹主角，物体改为纯碰撞交互 |
| Boss三态逻辑复杂 | 中 | 第5关延期 | 降级为单态Boss（仅有平静态+弹幕），飓风期改为场景固定事件 |
| 美术产能不足 | 高 | 关卡使用占位素材 | 接受占位素材上线。美术工作不阻塞关卡搭建——先搭玩法，后换皮 |
| 关卡难度曲线不理想 | 中 | 玩家体验差 | D13测试后集中调整：加/减敌人、调整检查点间距、延长能量回复时间 |
| 成员行程冲突 | 低 | 某角色进度落后 | 程序A可接手程序B工作（共用架构），关卡组互相备份 |
